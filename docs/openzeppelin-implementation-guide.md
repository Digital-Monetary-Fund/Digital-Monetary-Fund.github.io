# OpenZeppelin Implementation Guide — DMF Stablecoin Portfolio

**Status:** Working draft — resolved decisions + open questions
**Companion to:** `token-standard-recommendation.md`
**Date:** 2026-05-12

## Scope

Practical guide for implementing the 205 DMF stablecoins on top of OpenZeppelin Contracts. Captures the design decisions resolved through review and the implementation patterns required for the OZ-specific work, including a complete reference template.

## 1. Naming convention (resolved)

| Field | Pattern | Examples |
|---|---|---|
| **Symbol** | `1` + ISO 4217 alpha code | `1USD`, `1AUD`, `1JPY`, `1EUR`, `1KWD` |
| **Name** | `1` + currency long name | `1 United States Dollar`, `1 Australian Dollar`, `1 Japanese Yen` |
| **`decimals()`** | Always `18` | (never the minor unit count — DEX/oracle compatibility) |
| **ISO 4217 numeric** | Stored as immutable `uint16` | 840 for USD, 392 for JPY, 414 for KWD |
| **Minor units** | ISO 4217 minor unit count, stored as `uint8` | See below |

### Minor unit counts (ISO 4217)

- **0** — JPY, KRW, VND, ISK, CLP, PYG, RWF, UGX, VUV, XAF, XOF, XPF
- **2** — USD, EUR, AUD, GBP, CAD, CHF, CNY, SGD, HKD (most currencies)
- **3** — KWD, BHD, OMR, JOD, TND, LYD, IQD
- **4** — CLF (Chilean unit of account)
- **5** — MGA (Malagasy ariary), MRU (Mauritanian ouguiya)

## 2. Initializer signature (resolved)

EIP-1167 clones require initializers, not constructors.

```solidity
function initialize(
    string  memory symbol_,         // "1USD"
    string  memory name_,           // "1 United States Dollar"
    uint8          minorUnits_,     // 2 for USD, 0 for JPY, 3 for KWD
    uint16         iso4217Numeric_, // 840 for USD
    address        admin_,          // DEFAULT_ADMIN_ROLE holder
    address        minter_,         // MINTER_ROLE (reserve attestation contract)
    address        pauser_          // PAUSER_ROLE (slow multisig)
) external initializer;
```

`decimals_` is **not** a parameter — `decimals()` is overridden to always return `18`.

## 3. Banker's rounding behaviour (resolved)

### Scope

| Function | Rounding? | Why |
|---|---|---|
| `_mint` | None | Reserve attestations / accruals can produce 18-dp values; issuance is precise |
| `_burn` | None | Token accepts any value; the redemption gateway enforces fiat-minor-unit alignment at the application layer |
| `transfer` / `transferFrom` | Banker's rounding with insufficient-balance fallback | The only place fiat-shaped UX matters |
| `_update` | Not touched | Mint/burn paths stay precise; no `from == address(0)` branching needed |

### Algorithm

1. Compute `bankersRound(amount)` — round to nearest minor unit; on exact half, round to even.
2. If `bankersRound(amount) > balanceOf(from)`, fall back to `roundDown(amount)` (always ≤ amount, always ≤ balance).
3. Move the resulting amount; the `Transfer` event carries the actually-moved value, not the requested input.

### Behavioural consequences for integrators

- The input to `transfer()` is a **maximum**, not a guarantee.
- Balances can carry sub-minor-unit residue (from `_mint` and from DeFi swap outputs received from non-DMF tokens before any rounded transfer). Wallets display the raw balance.
- A `transferAll(to)` helper rounds the balance down before transferring, leaving the dust in the sender's account and avoiding the fallback path.
- From a DEX perspective, the token is effectively **fee-on-transfer**:
  - Uniswap V2 — supports with explicit handling
  - Uniswap V3 — excludes from concentrated liquidity
  - Curve — generally rejects
  - Aave / Compound — won't wrap cleanly

This is a deliberate tradeoff in service of fiat-faithful transfer semantics.

## 4. Token contract composition

### Generated by OZ Wizard

Use [wizard.openzeppelin.com](https://wizard.openzeppelin.com) for the scaffold, selecting:

- **ERC20** (base)
- **Mintable** — supply tracks reserve backing
- **Burnable** — for redemptions
- **Pausable** — emergency freeze, held by slow multisig
- **Permit** — EIP-2612 gasless approvals
- **Access Control: Roles** (not Ownable) — `MINTER_ROLE`, `PAUSER_ROLE`, `DEFAULT_ADMIN_ROLE`
- **Upgradeability: None** — immutable token; upgradeable Escrow and oracle modules separately

Don't select:
- **Flash Mint** — incompatible with asset-backed supply
- **Votes** — different use case (governance token, not stablecoin)
- **Premint** — supply tracks backing, not minted upfront

### Use the `-Upgradeable` variants for clone compatibility

Even though the token itself isn't upgradeable, EIP-1167 clones require the implementation to use initializers rather than constructors. That means the `-Upgradeable` contract family:

```solidity
import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/ERC20Upgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20BurnableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20PausableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20PermitUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/AccessControlUpgradeable.sol";
```

### Add manually (not in Wizard)

- **ERC-1363 (`transferAndCall`)** — Vittorio Minacori's `erc-payable-token` library, OZ-style and OZ-compatible. Add alongside the standard ERC-20 interface, not instead of it.
- **Banker's rounding override** — see §5.

## 5. Reference template (Solidity)

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/ERC20Upgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20BurnableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20PausableUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/token/ERC20/extensions/ERC20PermitUpgradeable.sol";
import "@openzeppelin/contracts-upgradeable/access/AccessControlUpgradeable.sol";

/// @title  DMF Stablecoin Template
/// @notice ERC-20 stablecoin with banker's rounding applied at transfer time
///         to mimic fiat minor-unit precision. Decimals are always 18 for
///         ecosystem compatibility; rounding is configured via `minorUnits`.
contract DmfStablecoin is
    Initializable,
    ERC20Upgradeable,
    ERC20BurnableUpgradeable,
    ERC20PausableUpgradeable,
    ERC20PermitUpgradeable,
    AccessControlUpgradeable
{
    bytes32 public constant MINTER_ROLE = keccak256("MINTER_ROLE");
    bytes32 public constant PAUSER_ROLE = keccak256("PAUSER_ROLE");

    uint8   public minorUnits;       // 2 for USD, 0 for JPY, 3 for KWD, etc.
    uint16  public iso4217Numeric;   // 840 for USD, 392 for JPY, 414 for KWD
    uint256 private _roundingUnit;   // cached 10**(18 - minorUnits)

    /// @custom:oz-upgrades-unsafe-allow constructor
    constructor() {
        _disableInitializers();
    }

    function initialize(
        string  memory symbol_,
        string  memory name_,
        uint8          minorUnits_,
        uint16         iso4217Numeric_,
        address        admin_,
        address        minter_,
        address        pauser_
    ) external initializer {
        require(minorUnits_ <= 18, "minorUnits > 18");
        require(admin_  != address(0), "admin = 0");
        require(minter_ != address(0), "minter = 0");
        require(pauser_ != address(0), "pauser = 0");

        __ERC20_init(name_, symbol_);
        __ERC20Burnable_init();
        __ERC20Pausable_init();
        __ERC20Permit_init(name_);
        __AccessControl_init();

        minorUnits     = minorUnits_;
        iso4217Numeric = iso4217Numeric_;
        _roundingUnit  = 10 ** (18 - minorUnits_);

        _grantRole(DEFAULT_ADMIN_ROLE, admin_);
        _grantRole(MINTER_ROLE,        minter_);
        _grantRole(PAUSER_ROLE,        pauser_);
    }

    // ----- Decimals -----

    /// @notice Always 18. The minor-unit precision lives in transfer rounding,
    ///         not in `decimals()`, to preserve DEX / oracle compatibility.
    function decimals() public pure override returns (uint8) {
        return 18;
    }

    // ----- Mint / Burn (no rounding) -----

    function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) {
        _mint(to, amount);
    }
    // burn() / burnFrom() inherited from ERC20BurnableUpgradeable; the
    // redemption gateway enforces minor-unit alignment at the application layer.

    // ----- Pause -----

    function pause()   external onlyRole(PAUSER_ROLE) { _pause();   }
    function unpause() external onlyRole(PAUSER_ROLE) { _unpause(); }

    // ----- Transfer overrides: banker's rounding with insufficient-balance fallback -----

    /// @notice Input `amount` is a MAXIMUM. Actual moved amount = `_roundForTransfer(amount)`.
    function transfer(address to, uint256 amount)
        public override returns (bool)
    {
        uint256 rounded = _roundForTransfer(amount, balanceOf(_msgSender()));
        return super.transfer(to, rounded);
    }

    /// @notice Allowance is spent for the rounded amount, not the input amount.
    function transferFrom(address from, address to, uint256 amount)
        public override returns (bool)
    {
        uint256 rounded = _roundForTransfer(amount, balanceOf(from));
        return super.transferFrom(from, to, rounded);
    }

    /// @notice Convenience for "send max": rounds the sender's full balance down
    ///         before transferring. Never triggers the fallback path; dust (if any)
    ///         remains in the sender's account.
    function transferAll(address to) external returns (bool) {
        uint256 unit    = _roundingUnit;
        uint256 amount  = (balanceOf(_msgSender()) / unit) * unit;
        return super.transfer(to, amount);
    }

    /// @notice Banker's rounding (half-to-even) with fallback to round-down
    ///         when the rounded-up value would exceed `senderBalance`.
    function _roundForTransfer(uint256 amount, uint256 senderBalance)
        internal view returns (uint256 rounded)
    {
        uint256 unit = _roundingUnit;
        if (unit == 1) return amount;          // minorUnits == 18, no rounding

        uint256 quotient  = amount / unit;
        uint256 remainder = amount % unit;
        uint256 half      = unit / 2;

        if (remainder < half) {
            rounded = quotient * unit;
        } else if (remainder > half) {
            rounded = (quotient + 1) * unit;
        } else {
            // Exactly half — round to even
            rounded = (quotient % 2 == 0)
                ? quotient * unit
                : (quotient + 1) * unit;
        }

        // Insufficient-balance fallback: round down the *original* amount
        if (rounded > senderBalance) {
            rounded = quotient * unit;
        }
    }

    // ----- Required multi-inheritance override -----

    function _update(address from, address to, uint256 value)
        internal override(ERC20Upgradeable, ERC20PausableUpgradeable)
    {
        super._update(from, to, value);
    }
}
```

### Why `_transfer` is *not* the override point

Overriding the internal `_transfer` would catch both `transfer` and `transferFrom`, which sounds cleaner. The problem: in `transferFrom`, allowance is spent *before* `_transfer` runs, against the unrounded input. The user authorised allowance `X`; rounding would move `Y < X` but burn `X` from allowance — a real bug.

Overriding the public `transfer` / `transferFrom` and passing the rounded amount into `super` is the correct entry point — allowance is spent against the rounded value.

## 6. Factory with EIP-1167 clones + CREATE2

OZ's `Clones.sol` deploys minimal proxies at ~45k gas vs ~1.5M for full deployments. Essential at 205 currencies.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import "@openzeppelin/contracts/proxy/Clones.sol";
import "@openzeppelin/contracts/access/AccessControl.sol";
import {DmfStablecoin} from "./DmfStablecoin.sol";

contract DmfStablecoinFactory is AccessControl {
    bytes32 public constant DEPLOYER_ROLE = keccak256("DEPLOYER_ROLE");

    address public immutable implementation;
    mapping(uint16 => address) public byIso4217;   // numeric code → token address

    event StablecoinDeployed(
        uint16  indexed iso4217,
        string          symbol,
        address         token
    );

    constructor(address implementation_, address admin_) {
        require(implementation_ != address(0), "impl = 0");
        implementation = implementation_;
        _grantRole(DEFAULT_ADMIN_ROLE, admin_);
        _grantRole(DEPLOYER_ROLE,      admin_);
    }

    /// @notice Deploys a new currency clone at a deterministic CREATE2 address.
    ///         `salt` should be a stable string like keccak256("DMF-1USD-v1") so
    ///         the same currency lands at the same address on every EVM chain.
    function deploy(
        string  calldata symbol_,
        string  calldata name_,
        uint8            minorUnits_,
        uint16           iso4217Numeric_,
        address          admin_,
        address          minter_,
        address          pauser_,
        bytes32          salt
    ) external onlyRole(DEPLOYER_ROLE) returns (address token) {
        require(byIso4217[iso4217Numeric_] == address(0), "Already deployed");

        token = Clones.cloneDeterministic(implementation, salt);
        DmfStablecoin(token).initialize(
            symbol_, name_, minorUnits_, iso4217Numeric_,
            admin_, minter_, pauser_
        );

        byIso4217[iso4217Numeric_] = token;
        emit StablecoinDeployed(iso4217Numeric_, symbol_, token);
    }

    function predictAddress(bytes32 salt) external view returns (address) {
        return Clones.predictDeterministicAddress(implementation, salt, address(this));
    }
}
```

### Cross-chain address matching

For `1USD` to land at the same address on Ethereum and BSC:

1. Deploy a known CREATE2 deployer at the same address on both chains (e.g. CreateX at `0xba5Ed...`, or your own deployer with a synchronized EOA nonce).
2. Deploy `DmfStablecoin` implementation via CREATE2 with a fixed salt — same address on both chains.
3. Deploy `DmfStablecoinFactory` via CREATE2 with a fixed salt — same address on both chains.
4. Call `factory.deploy(..., salt: keccak256("DMF-1USD-v1"))` on both chains.

Because the factory address, implementation address, and salt all match, `Clones.cloneDeterministic` produces the same clone address on both chains.

## 7. Access control topology (open — needs decision)

Three roles per token: `DEFAULT_ADMIN_ROLE`, `MINTER_ROLE`, `PAUSER_ROLE`. At 205 tokens, the question is who holds each.

| Topology | Pros | Cons |
|---|---|---|
| **One multisig holds all roles across all 205** | Simplest ops | Single point of failure; one compromise = 205 tokens at risk |
| **One multisig per role, shared across 205** | Role separation; smaller blast radius | Still concentrated per role |
| **Per-currency role holders** | Maximum isolation | 615 keys to manage |
| **MINTER_ROLE = reserve attestation contract** | Automated mints; no human in the issuance path | Attestation oracle becomes systemic dependency |

**Proposed default (pending review):** one Safe multisig per role, shared across all 205. MINTER_ROLE held by an attestation-gated contract that the admin multisig configures. Revisit per-currency separation only if a jurisdiction requires it.

## 8. Reserve attestation gating (open — needs decision)

Wrap MINTER_ROLE in a contract that caps `mint()` by attested reserve. Options:

- **Chainlink Proof-of-Reserve** — mature, established feeds. May not cover all 205 fiat currencies.
- **Auditor-signed attestation oracle** — auditor signs `(currency, reserve_amount, timestamp)`; contract verifies signature and caps mint. Cheaper, less decentralised, depends on auditor uptime.
- **Hybrid** — Chainlink for currencies it covers, signed attestation for the long tail.

**Pending decision** on auditor relationship and attestation cadence (real-time / daily / weekly).

- **Foundry** — build, test, fuzz. Better than Hardhat for ERC-20 invariant testing; OZ contracts work out of the box.
- **OpenZeppelin Defender** — post-deployment ops: Safe multisig integration, automated mint triggers from attestation events, monitoring, alerts. Worth the subscription at 205 contracts.
- **Slither + Mythril** — static analysis before audit submission.
- **OZ Upgrades Plugin** — only needed for the *Escrow* and *attestation* contracts, since the token itself is not upgradeable.

## 10. Audit scope

The clone pattern's biggest win: one template audit covers all 205 clones. Scope:

1. `DmfStablecoin` implementation contract (the template) — including the rounding override
2. `DmfStablecoinFactory` — including CREATE2 / clone determinism
3. Escrow contract (separate doc / specification)
4. Reserve attestation contract / oracle integration
5. Cross-chain deployment scripts (CREATE2 salt management, deployer nonce sync)

OZ's contract audits cover the inherited base. The composition, the `_roundForTransfer` logic, and the factory are new surface and need independent review.

Re-engage Coinscope / CoinTool / OpenZeppelin (or pick a single firm for portfolio coverage) before mainnet deployment of the new template.
